It is called a stack. Is it like VStack?

Part 1 · Not a layout stack

NavigationStack is not a VStack

Two different jobs
  • VStack: arranges children vertically
  • NavigationStack: manages a hierarchy of destinations
iOS 26.5 SDK, SwiftUI interface (simplified)

public struct NavigationStack<Data, Root> : View where Root : View {
  public init(@ViewBuilder root: () -> Root) where Data == NavigationPath
  public init(path: Binding<NavigationPath>, @ViewBuilder root: () -> Root)
  …
}

SAY

The name says stack, but this is not a layout stack. A VStack arranges several children vertically, and all of them are on screen together. A NavigationStack manages a hierarchy of navigation destinations: the root, then whatever has been pushed on top. One destination is visible at a time; the earlier ones sit behind it in the hierarchy.

SAY

Click: the declaration from the SDK, what Command-click shows, simplified. It is generic over Data and Root. The plain init takes only the root content; then Data is NavigationPath, a list of destinations SwiftUI keeps for you. The second init takes a path binding: navigation driven by your own state. That is Part 2.

SAY

Both are interactive, and both can show the words Send Money, but they express different intentions. A Button represents an action: run this closure. A NavigationLink declares a destination: this is where tapping takes you.

SAY

How does this compare with UIKit, and what happens to memory?

Part 1 · NavigationStack versus UINavigationController

Same idea, declarative API

UIKitSwiftUI
UINavigationControllerNavigationStack
pushViewControllerNavigationLink or a path update
popViewControllerBack navigation or a path update
UIViewController objectsView descriptions and navigation state
Imperative navigation APIDeclarative navigation API
  • SwiftUI may use UIKit internally on iOS
  • No fixed one-to-one mapping to view controllers
  • Use the public navigation APIs
SAY

In UIKit, navigation is commonly built with UINavigationController: you create view controller objects and call pushViewController and popViewController, an imperative API. SwiftUI’s NavigationStack is a declarative abstraction: you describe destinations with links, or with a path, which is Part 2, and SwiftUI performs the pushes and pops. View controllers become view descriptions plus navigation state.

SAY

Click: the insight. On iOS, SwiftUI may integrate with UIKit internally, but do not assume a fixed one-to-one mapping between SwiftUI destinations and UIKit view controllers. Use the public navigation APIs unless you have a specific interoperability need; Unit 10 covers UIKit integration.

Part 2 · A router of our own

The path, moved into an object

NPayRouter.swift
@MainActor
@Observable
final class NPayRouter {
    var path: [NPayRoute] = []

    func push(_ route: NPayRoute) {
        path.append(route)
    }

    func pop() {
        guard !path.isEmpty else { return }
        path.removeLast()
    }

    func popToRoot() {
        path.removeAll()
    }
}

Part 3 · TabView and NPayRouter together

One router: a selection and four paths

App/NPayRouter.swift (condensed)
enum NPayRoute: Hashable {
    case accountDetails, settings
    case paymentSuccess(UUID), transactionDetails(UUID)
}

@MainActor @Observable
final class NPayRouter {
    var selectedTab: NPayTab = .home
    var homePath: [NPayRoute] = []
    var paymentsPath: [NPayRoute] = []
    var historyPath: [NPayRoute] = []
    var profilePath: [NPayRoute] = []

    func select(_ tab: NPayTab) { selectedTab = tab }

    func showPaymentSuccess(_ id: UUID) {
        selectedTab = .payments
        paymentsPath.append(.paymentSuccess(id))
    }

    func returnHome() {
        paymentsPath.removeAll()
        selectedTab = .home
    }
}
Why separate paths
  • Home → Account Details; History → a transaction
  • Back on Home: still on Account Details
  • One shared path makes that hard
@MainActor
  • Navigation state drives UI: mutate it on the main actor
@Observable
  • SwiftUI tracks the properties it reads
  • In depth: Unit 4
SAY

Part 3 · Where should balance and transactions live?

Not in a tab: in a shared store

Store/NPayStore.swift
@MainActor
@Observable
final class NPayStore {
    var balancePaise = 2_500_000
    var transactions: [Transaction] = []

    func recordDemoPayment(recipient: String,
                           amountPaise: Int) -> UUID? {
        let trimmed = recipient.trimmingCharacters(
            in: .whitespacesAndNewlines)
        guard !trimmed.isEmpty, amountPaise > 0,
              amountPaise <= balancePaise else { return nil }
        let id = UUID()
        balancePaise -= amountPaise
        transactions.insert(
            Transaction(id: id, title: "Sent to \(trimmed)",
                        amountPaise: -amountPaise, date: .now),
            at: 0)
        return id
    }
}

one change in a token reaches everything that uses it

Generic, not erased
Content: View + @ViewBuilder; real types like TupleView
