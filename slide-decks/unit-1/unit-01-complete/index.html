Part 1 · SIL and LLVM

What SIL and LLVM do

SIL · Swift Intermediate Language

A representation designed for Swift. It keeps Swift’s semantics so the compiler can check and optimize them before lowering the code further.

LLVM

A compiler infrastructure project. Swift uses it to optimize and generate native machine code for each supported target.

Our six lines, compiled with swiftc -O (Swift 6.3, arm64):

StageWhat we seeMeaning
SILsmul_with_overflow_Int64Swift semantics kept: the multiply is overflow-checked
LLVM IRstore i64 1500LLVM worked out 500 × 3 at compile time
Assemblymov w20, #1500one processor instruction loads the answer
SAY

SIL stands for Swift Intermediate Language: an intermediate representation designed specifically for Swift. It lets the compiler represent Swift semantics and optimize them before lowering the code further. LLVM is a compiler infrastructure project; Swift uses it to optimize and generate native machine code for each supported target.

SAY

Click: real output from our six lines. In SIL the multiply is still there, as an overflow-checked multiply: Swift traps on integer overflow instead of silently wrapping, and SIL carries that rule. In LLVM IR the optimizer has already computed 500 times 3, so it just stores 1500. The arm64 assembly loads 1500 with a single instruction. You will reproduce this in the lab.

Convert on purpose, know what you lose

Convert.swift

Part 2 · Model

NPay’s first model

BankAccount.swift
struct BankAccount {
    let accountNumber: String
    var balanceMinor: Int64          // paise
    mutating func deposit(_ amountMinor: Int64) {
        guard amountMinor > 0 else { return }
        let (sum, overflow) = balanceMinor.addingReportingOverflow(amountMinor)
        guard !overflow else { return }
        balanceMinor = sum
    }
}
var account = BankAccount(accountNumber: "NP1001", balanceMinor: 2_500_000)
account.deposit(50_000)          // balanceMinor is now 2550000
mutating
  • Needed to change a struct’s stored properties
Guards
  • Only positive deposits
  • Detect overflow, don’t trap
Production
  • Throw errors (Part 7)
  • The server processes transactions
SAY

A struct with a constant account number and a variable balance in paise. deposit introduces a new keyword: mutating. A struct method that modifies stored properties must be marked mutating, because it changes the value itself.

SAY

Click: the model checks that the deposit is positive, and uses addingReportingOverflow so an overflow is detected instead of crashing the app. Depositing 50,000 paise, ₹500, gives 2,550,000.

SAY

Click: this is a teaching model. A production banking system would throw explicit errors instead of silently returning, and the server, not the app, processes transactions. Part 7 covers error handling.

Part 5 · Copy-on-write

Share until someone writes

CopyOnWrite.swift

Afterfalse: separate buffers

  • Value semantics, without copying on every assignment

  • Built into Array, Dictionary, Set, String
SAY

Part 10 · Transfer

All the checks, then both writes, no await

BankLedger+Transfer.swift
func transfer(_ amount: Money, from sourceId: String, to destinationId: String) throws {
    guard sourceId != destinationId else { throw BankingError.sameAccountTransfer }
    guard amount.paise > 0 else { throw BankingError.invalidAmount }
    guard var source = accounts[sourceId],
          var destination = accounts[destinationId] else { throw BankingError.accountNotFound }
    guard source.isActive, destination.isActive else { throw BankingError.accountInactive }
    guard source.balance.paise >= amount.paise else { throw BankingError.insufficientFunds }
    let (newDest, overflow) = destination.balance.paise.addingReportingOverflow(amount.paise)
    guard !overflow else { throw BankingError.arithmeticOverflow }
    source.balance = Money(paise: source.balance.paise - amount.paise)
    destination.balance = Money(paise: newDest)
    accounts[sourceId] = source
    accounts[destinationId] = destination          // no await anywhere above
}
Safe here because
  • The actor owns both accounts
  • No await between check and change
SAY

A transfer changes two accounts: the source goes down, the destination goes up, as one logical operation. The method checks everything first: not the same account, a positive amount, both accounts exist and are active, enough funds, and no overflow at the destination. Only then does it write both accounts.

SAY

SAY

Part 10 · Reentrancy

Check, await, change: the check goes stale

AccountStore.swift
actor AccountStore {
    var balancePaise: Int64 = 1_000_000            // ₹10,000

    func withdraw(_ amountPaise: Int64) async throws {
        guard balancePaise >= amountPaise else {
            throw BankingError.insufficientFunds
        }
        await performExternalCheck()     // others may run
        balancePaise -= amountPaise
    }
}
Real runs

check, await, change → both ok, ₹−3,000
await, then check + change → one rejected, ₹4,000

  • Actor isolation does not make a multi-step async operation atomic
SAY

An actor lets one task in at a time, but it is reentrant: at an await, the actor is free to run other calls. This AccountStore checks the balance, then awaits an external check, then subtracts.

SAY

Click through: A checks ₹10,000 against ₹7,000: fine. A awaits the external check, and the actor is free. B checks ₹10,000 against ₹6,000: fine, but stale, because A has not paid yet. A pays, then B pays. Click: −₹3,000.

SAY

Click: we ran both versions. Check, await, change: both withdrawals succeeded and the balance went to minus ₹3,000. Await first, then check and change together with no suspension in between: one was rejected and ₹4,000 remained. That is why our BankLedger’s transfer has no await inside it, and why its concurrency test passed.

SAY

The rule: never assume actor isolation makes a multi-step asynchronous business operation atomic. Keep validation and mutation together without suspension, or re-validate after the await. In a real bank this is a database and business-consistency problem; Lesson 8.4 goes deeper.
